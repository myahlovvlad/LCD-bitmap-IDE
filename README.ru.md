# LCD-bitmap IDE

[Read in English](README.md)

**LCD-bitmap IDE** — офлайн-рабочая среда для проектирования монохромных embedded HMI-проектов: LCD-экраны, навигация на основе конечного автомата (FSM), привязки кнопок, runtime-теги, процедуры, аварии и готовые к прошивке экранные ресурсы.

Проект рассчитан на embedded UI-инженеров, разработчиков прошивок, команды, прототипирующие лабораторные приборы, и технических писателей, которым нужен один детерминированный исходный файл для небольшого дисплейного workflow. Портативный файл `.lcdproj` хранит вместе визуальную LCD-модель, поведение FSM, реестр текстов, runtime-метаданные и настройки экспорта.

## Область применения

LCD-bitmap IDE помогает проектировать и проверять операторский интерфейс вокруг workflow измерения или управления прибором:

- моделирование состояний setup, run, result, warning, error и service;
- отрисовка пиксель-точных монохромных LCD-экранов 128×64;
- привязка физических кнопок и runtime-тегов к поведению FSM;
- предпросмотр workflow до интеграции с целевым оборудованием;
- экспорт экранных ресурсов для embedded-прошивок;
- предоставление локальным LLM-агентам возможности инспектировать и редактировать открытый проект через REST или MCP.

Приложение не выполняет физические измерения само по себе. Реальный сбор данных требует собственной прошивки прибора, backend-сервиса или аппаратного коннектора.

## Новое в этом релизе

- **FSM Mermaid ↔ Python DSL round-trip.** Граф FSM (состояния, переходы, события, раскладка) можно выгрузить в детерминированный текст Mermaid или Python DSL (`export_fsm_script`), отредактировать, получить предпросмотр семантического diff (`preview_fsm_script_import`) и применить одной отменяемой транзакцией (`apply_fsm_script_import`).
- **Headless-сценарии `run_fsm_scenario`.** Скриптовая последовательность событий/нажатий кнопок/записей тегов проигрывается против свежего headless-движка симуляции — независимо от того, открыта ли панель Runtime — и возвращает детерминированную пошаговую трассу (состояние до/после, id перехода, статус процедуры, заблокирован ли шаг и почему).
- **UX Semantic Contract.** Типизированная, версионированная UX-метамодель проекта (`project.uxContract`): роль и назначение каждого экрана/состояния/перехода/элемента управления, единый словарь терминологии, пользовательские цели (user goals), политики и скриптовые UX-сценарии. Для старых проектов при миграции создаётся пустой, полностью заполненный контракт — без новых блокирующих ошибок.
- **Детерминированный UX-анализатор `analyze_project_ux`.** 37 правил по пяти категориям (структура/связи, навигация и восстановление, семантика/терминология, безопасность, сценарии/трассируемость) плюс визуальные проверки на основе существующего конвейера рендера. Каждая находка трассируется к конкретным id экрана/состояния/перехода/элемента управления, список находок детерминирован и никогда не блокирует не связанные с ним правки FSM/экранов.
- **Необязательный, не блокирующий LLM-обзор.** `export_project_ux_review_packet` формирует самодостаточный пакет для внешней LLM; `import_project_ux_review` принимает строго типизированный JSON-ответ и превращает его в эвристические находки (`source: "heuristic_llm"`) — по схеме они не могут иметь severity `"error"` и никогда не сохраняются в проект.

Подробности архитектуры и словарь правил — в [docs/UX_SEMANTIC_VALIDATION.md](docs/UX_SEMANTIC_VALIDATION.md) (на английском).

## Проверка UX-семантики проекта

`uxContract` — это типизированный, отдельный от исполняемой структуры FSM/экранов слой смысла: какую роль играет экран, что означает элемент управления, какая пользовательская цель за ним стоит, какая политика безопасности должна соблюдаться. FSM и экраны остаются единственным источником истины по тому, что реально происходит; `uxContract` не может подменить или разойтись с этим — при миграции все ссылки на удалённые id тихо отбрасываются.

Анализатор `analyze_project_ux` детерминированно проверяет, в частности:

- есть ли у состояния с ролью «ошибка» путь возврата (recovery path) в исходное/навигационное состояние;
- требует ли деструктивное действие (`riskLevel: destructive/critical`) явного подтверждения;
- совпадает ли фактически доступный на экране/переходе набор действий с ожидаемым/запрещённым по контракту;
- согласована ли терминология: один и тот же intent не должен подписываться разными словами на разных экранах, и наоборот;
- насколько полно проект размечен (coverage): доля экранов с ролью, состояний с назначением, переходов с intent, error-состояний с recovery-путём, критических целей со сценарием.

**Большое число находок на только что мигрированном или ранее не размеченном проекте — ожидаемое исходное состояние, а не признак дефекта движка.** Пока `uxContract` пуст, анализатор честно сообщает: роль не указана, назначение не указано, покрытие 0/N. Это отправная точка для последующей семантической разметки, а не диагноз о качестве самого FSM/экранов.

## Где искать UX Validation

В десктоп-приложении откройте нужный проект, затем в панели навигации workspace откройте вкладку **UX Validation** (иконка щита). На вкладке:

- сводный вердикт (`pass` / `needs_review` / `fail`) и счётчики находок по severity;
- метрики покрытия по категориям (роли экранов, назначение состояний, intent переходов и т. д.);
- фильтры по severity и категории;
- список находок с переходом к затронутому экрану/состоянию/переходу/элементу одним кликом;
- запуск анализа (в том числе со сценариями и визуальными проверками) кнопкой без обращения к Runtime Workspace;
- точка входа в редактирование `uxContract`.

То же самое доступно программно через REST/MCP — см. раздел «UX Validation» в [docs/API_MCP_CONNECTORS.md](docs/API_MCP_CONNECTORS.md).

## Быстрый старт из исходников

```bash
git clone https://github.com/myahlovvlad/LCD-bitmap-IDE.git
cd LCD-bitmap-IDE
npm ci
npm run electron:dev
```

Для браузерной разработки:

```bash
npm run dev
```

Откройте `http://127.0.0.1:5173`.

Для Tauri/Rust-приложения:

```bash
npm --prefix apps/tauri ci
npm run tauri:dev
```

Инсталлятор Tauri для текущей ОС собирается командой `npm run tauri:build`. Зависимости Electron и Tauri изолированы: Electron остаётся стабильным корневым приложением, а Rust-оболочка находится в [`apps/tauri`](apps/tauri/README.md).

## API и MCP

Electron- и Tauri-сборки предоставляют один и тот же локальный автоматизационный контракт:

- REST API: `http://127.0.0.1:8766`
- MCP endpoint: `http://127.0.0.1:8767/mcp`

Команды на изменение проекта требуют `expectedRevision`. Настройка коннекторов и агентных workflow — в [docs/API_MCP_CONNECTORS.md](docs/API_MCP_CONNECTORS.md).

## Границы безопасности

Публичная ветка намеренно очищена: она не содержит проприетарных проектов приборов, результатов реверс-инжиниринга прошивок, приватных логов, конфиденциальной документации, приватных ключей или коммерческих каталогов экранов.

REST и MCP серверы слушают только `127.0.0.1` и предназначены исключительно для локальной разработческой автоматизации. Не публикуйте эти порты через туннель.
