# План миграции LCD/HMI Editor на Rust и Tauri 2

## Краткое решение

Приложение можно выпускать для Windows, Linux и macOS на базе Rust.
Для текущего проекта оптимальна поэтапная миграция на Tauri 2:

- сохранить существующий интерфейс React/Vite и редакторы;
- заменить Electron-оболочку на Tauri;
- перенести файловые операции, COM-порт, вычисления, кодогенерацию и экспорт в Rust;
- некоторое время собирать Electron- и Tauri-версии параллельно;
- удалить Electron после проверки совместимости проектов и экспортируемых файлов.

Полностью переписывать GUI на нативный Rust-фреймворк технически возможно, но это
потребует повторной реализации canvas-редактора, диаграмм FSM, drag-and-drop,
локализации и большинства компонентов. Для задачи передачи макетов разработчикам
прошивки такой риск и объём не дают практического преимущества.

## Текущие архитектурные границы

Код уже разделён на области, которые удобно переносить независимо:

- `renderer` и `features` — React GUI и рабочие области;
- `domain` и `application` — модель проекта и команды приложения;
- `projectMigration` и `projectInterop` — совместимость и обмен проектами;
- `compiler` — нормализация, промежуточное представление и генераторы;
- `runtime` — симулятор и исполнение;
- `hmi-handoff` — пакет передачи макетов и ресурсов;
- Electron main/preload — доступ к ОС, файлам и последовательному порту.

## Целевая структура

```text
React/Vite GUI
    |
    | typed Tauri commands/events
    v
Rust application core
    |- project_io       открытие, сохранение, миграция и валидация проектов
    |- serial_ecros     COM-порт, CLI-протокол и поток событий прибора
    |- formula_engine   единые расчёты для прибора, симулятора и генератора C
    |- compiler         C/H/BIN и другие backend-экспортеры
    |- handoff          пакет экранов, шрифтов, строк и манифест для прошивки
    `- platform         диалоги, пути, журналирование и настройки ОС
```

Контракты команд должны быть узкими и версионированными. Данные между GUI и Rust
передаются как типизированные DTO с сериализацией JSON/Serde. Бинарные ресурсы
следует передавать файлами или массивами байтов, а длительные операции — через
события прогресса и отмену.

## Этапы миграции

### 1. Зафиксировать совместимость

- создать эталонные проекты и результаты экспорта;
- добавить golden-тесты для C/H/BIN, bitmap, шрифтов и пакета передачи;
- зафиксировать команды CLI спектрофотометра и ожидаемые ответы;
- сравнивать численные результаты Rust и текущего симулятора с заданным допуском.

### 2. Добавить Tauri параллельно Electron

- создать `src-tauri`;
- подключить существующую Vite-сборку без переделки GUI;
- реализовать системные диалоги, настройки и безопасный доступ к файлам;
- оставить Electron как временный проверенный канал сборки.

### 3. Перенести интеграцию с ОС и прибором

- открыть/создать/сохранить проект через Rust;
- реализовать перечисление и подключение COM-портов;
- перенести таймауты, повторные попытки, разбор CLI и журнал обмена;
- передавать состояния подключения и измерения в GUI событиями Tauri.

### 4. Перенести расчёты и генераторы

- сделать один Rust-модуль формул источником истины;
- вызывать его из симулятора;
- использовать ту же модель при генерации C-кода;
- перенести компилятор ресурсов и формирование пакета для разработчиков прошивки;
- подтвердить побайтовую или семантическую эквивалентность эталонных результатов.

### 5. Настроить нативные релизы

Рекомендуемая матрица CI:

| ОС runner | Основные артефакты |
|---|---|
| `windows-latest` | MSI и/или NSIS installer |
| `ubuntu-latest` | DEB, AppImage, при необходимости RPM |
| `macos-latest` | `.app` и DMG для нужных архитектур |

Сборку лучше выполнять на нативном runner каждой ОС. Для публичного распространения
понадобятся подпись Windows и Apple Developer signing/notarization для macOS.
Секреты сертификатов должны храниться только в защищённых секретах CI.

### 6. Удалить Electron

Electron можно удалить после выполнения критериев:

- старые проекты открываются без потерь;
- новые проекты повторно открываются на всех трёх ОС;
- результаты вычислений совпадают;
- экспорт C/H/BIN и HMI-пакетов проходит golden-тесты;
- COM-связь проверена на реальном приборе Windows и на доступных стендах других ОС;
- локализация RU/EN/ZH полностью работает в Tauri-сборке;
- есть подписанные установочные артефакты и инструкция отката.

## Риски и меры

- Различия последовательных портов между ОС: изолировать их в `serial_ecros` и
  тестировать протокол отдельно от физического транспорта.
- Несовпадение float-расчётов: определить точность, округление и эталонные векторы.
- Форматы шрифтов и bitmap: сохранять версию формата и проверять размеры/CRC.
- Права доступа Tauri: включать только необходимые capabilities.
- Регрессии проектов: не изменять исходный файл без резервной копии и миграции
  через новую версию схемы.

## Первый реализуемый инкремент

Первый небольшой релиз Tauri должен уметь:

1. запустить текущий React GUI;
2. создать, открыть и сохранить проект;
3. сохранить выбранный язык интерфейса;
4. выполнить один эталонный экспорт;
5. собрать неподписанные тестовые пакеты на Windows, Linux и macOS.

После этого можно переносить COM-порт и расчётное ядро без остановки развития
текущей Electron-версии.
